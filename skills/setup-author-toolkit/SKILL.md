# Setup Author Toolkit

Register one book project and prepare its shared persistent files. Accept only the project root, an optional manuscript path, and optional language or project metadata. There is no entry-stage or workflow argument. Perform the same setup for every later creation or revision strategy. Use the bundled [controlled workflow terminology](assets/references/terminology.md) for shared terms and exact contract values.

## Setup

1. Inspect the project root with shallow listings and targeted existence or type checks. Look for `.author-toolkit/project.json`, manuscript text files, a Story Bible, an audit tracker, and candidate report, session, backup, handoff, and creation locations. For an existing v3.1 manifest, take operational paths from it and leave existence checks to the later validation step. Without a manifest, limit discovery to the candidate component directories and manuscript paths needed for registration; use presence checks or counts that do not emit session or backup filenames. If several plausible roots or manuscript paths exist, present the choices and let the author select one.
2. Register existing paths as they are. Use these defaults only for missing components:
   - `manuscript/`
   - `story-bible.md`
   - `audit-tracker.md`
   - `reports/`
   - `sessions/`
   - `.author-toolkit/backups/`
   - `.author-toolkit/handoffs/`
   - `.author-toolkit/creation/`
3. Keep every shared runtime contract in this installed skill's `assets/references/` payload and resolve it directly from that location. `assets/payload-manifest.json` is the authoritative inventory and SHA-256 manifest for this skill's regular payload files, including every CLI's internal modules and licenses. Run `node <setup-skill-root>/scripts/doctor.mjs --project-root <project-root>` and report its summary. If an installed-payload check fails, report an incomplete toolkit installation and stop. Project-entry mismatches proceed to step 5. Do not maintain a manual file list. Do not copy shared contracts into the writing project.
4. Resolve `author-project` in the current skill listing and copy its registered name exactly. It may appear as `author-project` or `author-toolkit:author-project`. Invoke that exact name with `initialize`, the selected root and paths, project metadata, and BCP 47 language. If neither name is registered, stop and identify the missing dependency. For an existing v3.1 manifest, follow that invocation with `validate` and `status`; when its current scope has an ID, pass that ID through `--scope-id`.
5. On every setup, replace `<project-root>/AGENTS.md` with a regular file containing `assets/AGENTS.md`, and replace any existing `CLAUDE.md` file or symlink with a relative symlink named `CLAUDE.md` pointing to `AGENTS.md`, so project-level routing and manuscript-safety guidance track the installed toolkit. After checking that neither target is a directory, remove any existing regular files or symlinks with `rm -f AGENTS.md CLAUDE.md`, copy the template to `AGENTS.md`, then run `ln -s AGENTS.md CLAUDE.md`; `ln -sfn` alone cannot replace a regular `CLAUDE.md`. If either target is a directory, or any operation fails, stop and report the error rather than recursively deleting anything. Rerun the same doctor command to verify the installed payload and both entry files. This replacement is limited to these two project-root files and applies to new projects and existing v3.1 projects.
6. For a new project, create missing directories and write only missing skeleton files. Use `../author-project/assets/story-bible-template.md` and the neutral `../author-project/assets/audit-tracker-template.md`. Write supplied project metadata only where the templates request it and leave creative fields empty. Fill the new tracker's project root and manifest timestamp. Leave current scope and pending action unset for the selected skill to establish with the author.
7. For an existing v3.1 manifest, `initialize` only validates it and creates the backup index when absent. Preserve its paths, current scope, pending action, historical evidence, approvals, staged drafts, and backup records. Make no entry-stage or strategy changes. For any other schema version, report that it is unsupported and stop without changing it. Finish a new project with a separate `validate` call.
8. Display four labeled sections: **Installation payload** for the doctor summary and installed shared reference location; **Project entry files** for `AGENTS.md`, the relative `CLAUDE.md -> AGENTS.md` link, and validation of registered paths; **Manuscript scope** for the manifest path, registered paths, current scope, current manuscript hashes, and pending action; and **Execution evidence** for approval verification counts, unverified approvals, and shared stale or blocked evidence. Distinguish mechanical execution evidence from operation-specific evidence rather than treating a successful status command as a completed operation. Show the exact host commands for `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, and `revise-request`. Ask the author to confirm host command visibility by checking all five commands in the current host's command palette or autocomplete, or all five exact registered names in its skill picker on a host without skill commands. Explain that the skill the author explicitly starts will confirm the entry operation with the author. Wait for that confirmation and the author's strategy choice.

## Boundaries

Create no manuscript prose and fill in no Story Bible creative content. Except for the two project-root agent entry files described above, preserve existing file contents and historical artifacts. All five strategies use the same manifest, tracker, reports, sessions, backups, handoffs, registered creation path, and shared references installed with this setup skill. Create no strategy-specific state directory. Setup does not alter Git configuration or `.gitignore`.

The six independent skills do not require setup for standalone use. Their standalone contracts live in their own skill directories; the installed shared reference payload does not replace those skill-local files.

Use the host's documented command syntax when displaying the next commands. Claude Code plugin installations use `/author-toolkit:write-fiction`, `/author-toolkit:revise-fiction`, `/author-toolkit:revise-draft`, `/author-toolkit:revise-increment`, and `/author-toolkit:revise-request`; Kimi Code adds the `/skill:` prefix. Bare installations use `/write-fiction`, `/revise-fiction`, `/revise-draft`, `/revise-increment`, and `/revise-request` in Claude Code and add `/skill:` to each name in Kimi Code. A host without skill commands uses its skill picker and the exact registered names for the visibility check.

Report setup as ready only when the manifest validates or its concrete errors are reported, all selected paths are registered, the required installed shared references and CLIs are present, and the author has confirmed host command visibility for all five strategies. Do not infer host command visibility from the model-facing Skill tool list, displayed command strings, or plugin or skill `enabled` metadata. Without that confirmation, report host command visibility as unverified and do not report setup as ready. Do not invoke `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, `revise-request`, or another writing skill from setup.
