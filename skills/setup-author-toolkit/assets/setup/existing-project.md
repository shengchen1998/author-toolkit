# Existing-project setup

Use this branch only when `<project-root>/.author-toolkit/project.json` exists. Setup runs `doctor`, initialize, entry-file repair, and one diagnostic check. This reference, the bounded project cache, and the installed setup CLIs supply the complete procedure; `author-project` documents are reserved for new-manifest registration and later state operations.

1. For an existing v3.1 manifest, run `node <setup-skill-root>/scripts/initialize.mjs --project-root <project-root> --json` directly for the bounded projection and resolved operational paths; leave existence checks to validation. This is the only existing-project initialization implementation; do not read `author-project`'s initialization references. Preserve its paths, current scope, pending action, historical evidence, approvals, staged drafts, and backup records while creating only a missing backup index. An unsupported or schema-invalid manifest still stops before entry-file replacement. For any other schema version, report that it is unsupported and stop without changing it.
2. Once initialization's manifest-schema check passes, perform step 3's entry-file replacement even if later project-state validation fails, then follow it with step 3's single `check.mjs --diagnose` call using `--project-root`. When initialization returns a current scope, add `--scope-id <current-scope-id> --require-execution` to that same final diagnostic call; otherwise retain the ordinary form. Report a validation failure as a project-state blocker and a requested execution-gate failure as a blocker for evidence-dependent operations; neither changes a passing installation into an installation failure. Initialization exits 3 for this schema-valid project-validation failure, distinguishing it from exit 1 for an unsupported or invalid schema or another initialization failure; exit 3 does not make project validation successful. When validation fails, this same call supplies the bounded `recorded_unverified` projection, scope paths and hashes, current-hash verification when the scope check passes, and backup-index differences; report the failure without rerunning preflight, repeating the other inspection commands, or printing the complete manifest. Run standalone `validate.mjs` only when a validation failure requires its complete diagnostics; do not repeat it after a successful preflight.
   After that check reports `Navigation cache: reusable snapshot only`, read `PROJECT_STATE.md` for navigation only. When the check reports a stale cache or does not check the cache, use the bounded command results instead of reading the cache. A reusable cache remains a generation-time snapshot; its recorded next action and current-draft revision convergence statements remain unevaluated until the applicable gates pass.
3. Report the record locations and identity differences already returned by `initialize.mjs` or the diagnosis without repeating backup index inspection, repairing history, or inferring a migration; run `node <setup-skill-root>/scripts/writes.mjs check-index --manifest <project-root>/.author-toolkit/project.json --explain` only when the reported inconsistency was not already diagnosed. Make no entry-stage or strategy changes.
4. Preflight's default ordinary status uses the current scope ID when available and leaves unverified approvals nonblocking. Prefer its text summary for status gates. Add `--json` only for structured results, and add `--details` only when individual unverified approvals are needed. The text summary groups unverified approvals by operation and shows each group's first and last approval IDs; these endpoints do not imply a contiguous ID range. Setup uses ordinary status to inspect state without treating a pending-action operation as a current-draft revision convergence claim. For an existing project with a current scope, the final diagnostic check in step 2 has already requested the strict execution gate with that explicit scope ID. Before relying on a recorded current-draft revision convergence statement to recommend or enter `revise-request`, or to establish a previous scope for `revise-increment`, use that call's validation and execution-gate results; a project-validation failure prevents the later status and execution-gate stages and is itself sufficient to reject the recorded claim. Apply the other conditions in [Current-draft revision convergence](../../../revise-fiction/references/state-and-findings.md#current-draft-revision-convergence). If the strict command exits nonzero, do not present the scope as having reached current-draft revision convergence or recommend a dependent entry. Report the unverified approvals and show `revise-draft` for its evidence-recovery audit and author decision, not as a promise that rerunning revision will repair missing evidence. This execution check does not block ordinary setup, a current-scope review, or unrelated read-only work.

Return to step 4 of `../../SKILL.md` for the categorized setup report and author confirmation.
