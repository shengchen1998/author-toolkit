# Creation state and recovery

Load this reference for artifact writes, context fingerprints, commits, restores, imports, or damaged-state recovery.

## Registered layout

Resolve `paths.creation` against the project root. The default is `.author-toolkit/creation/`:

- `state/current.md`: living current summary and records;
- `state/chapters/`: living chapter records keyed to source hashes;
- `state/volumes/`: living volume or story-phase summaries keyed to child hashes;
- `batches/<batch-id>.json`: immutable accepted creation batches;
- `batches/<commit-id>.json`: recovery journals;
- `staging/<batch-id>/`: proposed, rejected, and superseded text outside the manuscript inventory.

Story state uses `story-state-schema.json`, batches use `creation-batch-schema.json`, and commits use `creation-commit-schema.json`. Validate the JSON envelope and human-readable story-state Markdown after every write. Before manually assigning creation timestamps or UTC-based IDs and filenames, run the shared [Timestamp](../../author-project/references/operations.md#timestamp) command once for the coherent write batch. Use `result.json` for `created_at`, `updated_at`, and equivalent JSON fields and `result.filename` for UTC-based filenames; never infer a new write time from an existing artifact's filename. The registered creation root is operational and excluded from manuscript inventory.

## State identity

Accepted manuscript text establishes observed facts. Story Bible records author intent. Keep both visible when they conflict and request a decision rather than silently overwriting either source. Draft baseline remains revision evidence; creation state supports continuation.

Before the first accepted manuscript, `state/current.md` uses `scope_id: null` and may cite the Story Bible and approved planning artifacts as sources. Chapter and volume records require an actual scope ID. The first successful commit replaces the null current-state scope with the confirmed manuscript scope.

Each chapter record names its source path and SHA-256, summary, and fact, character, timeline, object, thread, and constraint records. Volume and current records reference child artifacts by path and hash. A changed child invalidates its ancestors until they are rebuilt. Structural validation proves identity and currency, not semantic extraction completeness; reread relevant original passages for consequential decisions.

Rejected staging text never enters story state or manuscript scope. Preserve it until the author explicitly requests cleanup. Ordinary creation rejection requires exactly one current chapter-review `creation-rejection` approval for the exact rejected batch paths, with the same batch ID and dependency-fingerprint binding plus the unchanged starting `scope_fingerprint`; manuscript acceptance, scope acceptance, and other approval types do not authorize rejection. A rejected bootstrap batch has no starting scope and cannot complete as no-change while the manuscript remains empty; preserve its staging and continue with an approved nonempty creation batch or import followed by `revise-draft`. Keep one active batch per book.

After project migration, preserve every staged draft from the legacy project without publishing it or inferring acceptance. Explicitly reject it through the batch-bound `creation-rejection` decision, or first establish a current satisfied full-manuscript starting evaluation through `revise-draft`, then start one new `write-fiction` cycle and reapprove the exact staged bytes, recomputed dependency fingerprint, story-state differences, and complete publication scope through new manuscript and scope approvals. Pending action and legacy approvals do not authorize either route. `legacy-staging-decision-required` blocks bootstrap until explicit rejection because an empty manuscript cannot supply the starting evaluation required for reapproval. Independent full-manuscript recovery and an ordinary cycle with valid satisfied starting evidence remain available.

A legacy batch marked `rejected` is decided only when it is schema-valid, has `commit: null`, and names exactly one rejection approval ID whose valid tracker row is an approved chapter-review `creation-rejection`. The approval paths must equal the ordered batch paths. Its reason must match the batch ID, dependency fingerprint recomputed from the plan, actions, and input versions, and current scope fingerprint; nonempty scope IDs must match across the batch, approval, and current scope. An empty legacy project requires a null batch scope ID and the empty scope fingerprint. Missing decisions, wrong approval types, and any batch, scope, fingerprint, path, action, or input-version mismatch keep both bootstrap and ordinary cycle starts blocked even when satisfied starting evidence exists. A valid empty rejection permits bootstrap without publication; a valid nonempty rejection still requires the satisfied starting evaluation. `batch.status` and caller confirmation booleans never replace the decision, and diagnosis never rewrites the batch or tracker to manufacture one.

## Context and dependency fingerprints

Use chapter categories, record text, open threads, adjacent chapters, and host text search to select context. Do not require a vector store or another service. Record the selected inputs in the batch plan.

Compute the fingerprint as SHA-256 over UTF-8 `JSON.stringify` of an object with keys `plan`, `context`, and `files` in that order:

- `plan` is the exact plan summary;
- `context` is the array of `{path, version, version_type}` objects with keys in that order, sorted by `path`, then `version_type`, then `version`;
- `files` is the array of `{path, action, input_sha256}` objects with keys in that order, sorted by `path`.

On resume, recompute the fingerprint from current dependencies. Unrelated manuscript membership changes require a refreshed publication scope but do not invalidate the staged content. A changed included dependency requires re-review or a new approved plan.

## Commit protocol

1. Read the manifest, current scope, accepted batch, and approvals immediately before publication. Require exact operation, paths, input versions, and acceptance. Require exactly one current `creation-manuscript` approval and one current `creation-scope` approval, each with `status: "approved"` and `operation: "chapter-review"`; duplicate or missing types do not authorize publication. The manuscript approval names exactly the batch paths. The scope approval names the complete target paths in author-confirmed reading order and matches the snapshot's confirmation decision ID. In each approval reason, record whitespace-separated `batch_id=<batch-id>`, `dependency_fingerprint=<fingerprint>`, and `scope_fingerprint=<fingerprint>` tokens alongside the human explanation. Recompute the dependency fingerprint from the batch summary, context, actions, and input hashes, and the scope fingerprint from the complete ordered target paths and output hashes. Both approvals must match all three values; an approval for another batch or input version cannot be reused.
2. Recompute the dependency fingerprint and each existing target's hash. Require every create target to remain absent and every modify, delete, or reorder target to match its accepted input. Stop on any mismatch.
3. Invoke `author-project` with `record-backup` for every existing target. New files record expected absence instead of an invented original backup.
4. Write `<paths.creation>/batches/<commit-id>.json` with `status: "in_progress"` and every planned file action, input/output hash, backup ID, and `pending` status. Write the batch and journal atomically before touching manuscript text.
5. For each file, write staged content to a temporary sibling, verify its SHA-256, and rename it atomically. Apply only the accepted action. Mark it `written`, reread it, and then mark `verified`. Update the journal after every transition.
6. Publish accepted story-state differences and the resulting scope. The author's acceptance supplies the exact ordered paths and hashes; actual output must match them. Validate manuscript inventory, state artifacts, tracker, and scope.
7. Mark the journal `committed`, freeze the accepted batch with `status: "committed"`, update pending action and session state, and propagate evidence changes. Link the existing batch and journal to the active cycle through `transition-cycle`, using the commit ID as the operation ID and the complete current scope as target. If the cycle linked this batch while it was staged or awaiting author review, the accepted or committed reference with the same batch ID replaces that living reference and its hash instead of appending another batch reference. Accepted batches are immutable thereafter; a different batch ID remains a separate batch and cannot satisfy the one-accepted-batch rule. The operation records manifest `cycle_operation` before advancing the cycle and clears it only after final manifest coordination. A bootstrap commit records `scope_before_id: null`, derives its change set from the null starting scope, and routes the first nonempty publication to `revise-draft` for its initial full-manuscript evaluation. Ordinary creation instead preserves its starting snapshot and routes to `revise-increment`. The cycle references artifact identities and the derived change set; it does not duplicate or execute the file-transition protocol. Every creation cycle accepts one committed batch, including an explicitly approved multi-chapter batch, and cannot link another commit or return to `writing-plan` before completion. Local units can be reused only through the coverage rules. Full-book synthesis from the old scope is no longer current for the expanded book.

Multiple files are coordinated by the journal and cycle recovery records, not claimed as a single filesystem transaction. If the process stops, compare each actual target with its accepted input and output hashes. Report completed, pending, and unexpected actions. Leave `status: "interrupted"` and require an explicit author decision to continue or restore; never silently roll back. Do not link an interrupted or unverified journal as a completed creation publication. If publication completed but cycle linking stopped, run `author-project reconcile-cycle` for diagnosis and choose `resume-creation-publication` only for the exact commit. That direction reruns the normal batch, approval, journal, scope, and output checks without writing manuscript; pending action alone supplies no publication or restore approval. After project migration, a nonterminal legacy journal instead produces `legacy-commit-recovery-required` without an inferred active cycle. Run `reconcile-cycle` without a direction, complete the explicit continue or restore procedure for the actual journal and files, and rerun diagnosis before any dependent cycle work.

## Restore and repair

A restore approval is distinct from creation and edit approvals. Name the commit and exact files. Preserve current content in a safety backup, including files created by the batch. Restore modified originals, move created files into that safety backup before removing them from the manuscript, reverse accepted state differences, and establish a newly confirmed scope. Record restorations in the backup index and batch history.

For missing, malformed, or stale story state, rebuild only affected chapter records and their ancestors from actual text and immutable batches. Mark extracted differences proposed and obtain author confirmation before restoring the state to active use.

## Evidence changes

New membership, deletion, or reading-order changes require a new scope. Text-only changes can retain the scope ID with new input hashes and, on v3.2, a new scope fingerprint after author confirmation. Creating new paths before or between retained paths changes their absolute indexes but does not by itself create retained-path reorder transitions. Compare retained paths by relative order. An actual change to that relative order requires exact `reorder` actions with matching input and output hashes, plus author confirmation of the complete target reading order; insertion must not weaken that check. Preserve historical reports and their original scope IDs, scope snapshots, and inventory snapshots. Use coverage units and the living coverage index under the registered reports path to compose current local coverage. Recompute every affected whole-book synthesis; milestone and chapter summaries never substitute for final reading of actual manuscript text.

For external additions, modifications, deletions, or reading-order changes, run `author-project reconcile-manuscript` before dependent work. Supply the actual target scope or null empty target, exact story-state references, and an existing tracker `creation-import` decision bound to the reconciliation ID, inventory fingerprint, and scope fingerprint or null empty scope. Without an active cycle, also identify the previous scope explicitly. The operation writes only an immutable manuscript reconciliation and coordinated project state; it never writes manuscript and does not replace import, restore, backup, or input-hash safety procedures. During an active cycle it preserves the starting snapshot and derives the cumulative change set rather than accepting caller-supplied transitions. Bootstrap keeps `change_set.from_scope: null` across later imports and verified edits. Reconciliation previous scopes and execution input scopes form one ordered event chain in which every previous or input identity follows the preceding target or output identity, every event is verified once, and the final target equals current scope. A real creation commit joins through `scope_before_id` and `scope_after_id`; its output scope must pass the existing batch, journal, approval, and verified-transition checks before later reconciliation or execution can use it. Missing commits and forged output scopes remain blockers. Empty reconciliation may appear as an intermediate null target awaiting nonempty recovery; only that recovery carries `recovery_from_empty` and must route full-manuscript `revise-draft`. Evaluation does not assume reconciliations precede executions or require every event to use the same strategy.
