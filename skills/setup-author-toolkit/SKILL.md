# Setup Author Toolkit

Register one book project and prepare its shared persistent files. Accept only the project root, an optional manuscript path, and optional language or project metadata. There is no entry-stage or workflow argument. Perform the same setup for every later creation or revision strategy. For setup, read the bundled [controlled workflow terminology](assets/references/terminology.md)'s **Core terms** and **Contract values** sections for shared terms and exact contract values. Consult its **Operation identifiers** section by exact identifier when a reported pending action, group of unverified approvals, or backup-index difference uses one.

## Setup

1. Check only whether `<project-root>/.author-toolkit/project.json` exists. Run `node <setup-skill-root>/scripts/doctor.mjs --project-root <project-root>` and report its summary. If an installed-payload check fails, report an incomplete toolkit installation and stop; project-entry mismatches proceed to step 3. Select exactly one branch after this check: when the manifest exists, read only [Existing project](assets/setup/existing-project.md); otherwise read only [New project](assets/setup/new-project.md). The new-project branch uses `node <setup-skill-root>/scripts/inspect-root.mjs --project-root <project-root> --json` for bounded discovery; the existing-project branch goes directly to initialization without manuscript or historical-directory discovery. Keep every shared runtime contract in this installed skill's `assets/references/` payload and resolve it directly from that location. `assets/payload-manifest.json` is the authoritative inventory and SHA-256 manifest for this skill's regular payload files, including every CLI's internal modules and licenses. Do not maintain a manual file list, copy shared contracts into the writing project, print `payload-manifest.json` or the complete manifest, or emit complete session or backup listings.
2. Follow the selected branch's initialization procedure, then return here for the remaining common steps. Stop for a missing installed file or initialization failure; the existing-project branch explicitly handles exit 3 after an accepted v3.1 schema.
3. On every setup, run `node <setup-skill-root>/scripts/install-entry-files.mjs --project-root <project-root> --json`. This replaces `<project-root>/AGENTS.md` with a regular file containing `assets/AGENTS.md`, and replaces any existing `CLAUDE.md` file or symlink with a relative symlink named `CLAUDE.md` pointing to `AGENTS.md`, so language, explicit-entry routing, and manuscript-safety invariants track the installed toolkit. Detailed strategy routing lives in `ask-author`; operational procedures remain in the active skills and their references. The CLI checks both agent targets before writing, leaves correct entries unchanged, and atomically replaces other regular files or symlinks. If either agent target is a directory or special file, or any operation fails, stop and report the error rather than recursively deleting anything. This replacement is limited to these two project-root agent files and applies to new projects and existing v3.1 projects. The same invocation creates `<project-root>/START_HERE.md` from `assets/START_HERE.md` only when that path is absent, preserving every existing file, symlink, or directory with that name; this short navigation file points to the manifest, optional `PROJECT_STATE.md` cache, and status check. Complete both actions when the selected branch permits, including after an accepted v3.1 schema with later project-state validation failures. Then run `node <setup-skill-root>/scripts/check.mjs --project-root <project-root> --diagnose` once, adding the selected branch's strict-execution options to this same call when applicable. This read-only call is the final installation and project-state verification: it checks the payload once, verifies both repaired agent entry files, and includes status, the execution-recovery audit, and the cache's current-format check. Report its four independent states: **Installation** covers payload and project entry files; **Project state** covers project validation; **Strategy gate** covers the requested execution gate; **Host visibility** remains unverified until the author confirms it. Require `Installation: passed` before describing the toolkit as installed; these results do not require `START_HERE.md` to exist or match the installed template. A project-state or strategy-gate failure does not change that installation result. Report project-state failures as project blockers and failed requested gates as blockers for evidence-dependent operations, without repeating doctor or preflight. Do not reproduce a recorded next action from a cache marked stale.
4. Display four labeled sections: **Installation payload** for the initial doctor and final diagnostic-check payload summaries and installed shared reference location; **Project entry files** for the final `Entry files` result, `AGENTS.md`, the relative `CLAUDE.md -> AGENTS.md` link, the created or preserved `START_HERE.md`, and validation of registered paths; **Manuscript scope** for the manifest path, registered paths, current scope, current manuscript hashes, and pending action; and **Execution evidence** for approval verification counts, unverified approvals, and shared stale or blocked evidence. Include the four independent states from step 3 and, when installation passed but a project or requested-gate check failed, explicitly state that the toolkit is installed while the affected project-state or evidence-dependent operations are blocked. Distinguish mechanical execution evidence from operation-specific evidence rather than treating a successful status command as a completed operation. Describe a historical current-draft revision convergence statement as recorded, not verified, unless the selected branch's procedure for that state has been applied. Show the exact host commands for `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, and `revise-request`; for `revise-request`, apply the selected branch's current-draft revision convergence routing rule. Ask the author to confirm host command visibility by checking all five commands in the current host's command palette or autocomplete (in Codex, the `$` autocomplete), or all five exact registered names in its skill picker on a host without skill commands. Explain that the skill the author explicitly starts will confirm the entry operation with the author. Wait for that confirmation and the author's strategy choice.

## Boundaries

Create no manuscript prose and fill in no Story Bible creative content. Preserve existing file contents and historical artifacts, except for the two project-root agent entry files described above. `START_HERE.md` is create-only and never replaces existing content. All five strategies use the same manifest, tracker, reports, sessions, backups, handoffs, registered creation path, and shared references installed with this setup skill. Create no strategy-specific state directory. Setup does not alter Git configuration or `.gitignore`.

The six independent skills do not require setup for standalone use. Their standalone contracts live in their own skill directories; the installed shared reference payload does not replace those skill-local files.

Use `$write-fiction`, `$revise-fiction`, `$revise-draft`, `$revise-increment`, and `$revise-request` when displaying the next commands in Codex. Do not add a qualifier to these unqualified registered skill names.

Report setup as ready only when installation and project state pass, all selected paths are registered, and the author has confirmed host command visibility for all five strategies. A failed strategy gate blocks its dependent operations without making a passing installation incomplete. Do not infer host command visibility from model-facing registry metadata or displayed command strings. Without that confirmation, report host command visibility as unverified and do not report setup as ready. Do not start `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, `revise-request`, or another writing skill from setup.
