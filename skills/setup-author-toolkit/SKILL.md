# Setup Author Toolkit

Register one book project and prepare its shared persistent files. Accept only the project root, an optional manuscript path, and optional language or project metadata. There is no entry-stage or workflow argument. Perform the same setup for every later creation or revision strategy. For setup, read the bundled [controlled workflow terminology](assets/references/terminology.md)'s **Core terms** and **Contract values** sections for shared terms and exact contract values. Consult its **Operation identifiers** section by exact identifier when a reported pending action, group of unverified approvals, or backup-index difference uses one.

## Setup

1. Inspect the project root with shallow listings and targeted existence or type checks. Look for `.author-toolkit/project.json`, manuscript text files, a Story Bible, an audit tracker, and candidate report, session, backup, handoff, and creation locations; if several plausible roots or manuscript paths exist, present the choices and let the author select one. Keep every shared runtime contract in this installed skill's `assets/references/` payload and resolve it directly from that location. `assets/payload-manifest.json` is the authoritative inventory and SHA-256 manifest for this skill's regular payload files, including every CLI's internal modules and licenses. Do not maintain a manual file list, copy shared contracts into the writing project, print `payload-manifest.json` or the complete manifest, or emit complete session or backup listings. Run `node <setup-skill-root>/scripts/doctor.mjs --project-root <project-root>` and report its summary. If an installed-payload check fails, report an incomplete toolkit installation and stop; project-entry mismatches proceed to step 3. Select exactly one branch after this check: when `.author-toolkit/project.json` exists, read only [Existing project](assets/setup/existing-project.md); otherwise read only [New project](assets/setup/new-project.md).
2. Follow the selected branch's initialization procedure, then return here for the remaining common steps. Stop for a missing installed file or initialization failure.
3. On every setup, run `node <setup-skill-root>/scripts/install-entry-files.mjs --project-root <project-root> --json`. This replaces `<project-root>/AGENTS.md` with a regular file containing `assets/AGENTS.md`, and replaces any existing `CLAUDE.md` file or symlink with a relative symlink named `CLAUDE.md` pointing to `AGENTS.md`, so language, explicit-entry routing, and manuscript-safety invariants track the installed toolkit. Detailed strategy routing lives in `ask-author`; operational procedures remain in the active skills and their references. The CLI checks both targets before writing, leaves correct entries unchanged, and atomically replaces other regular files or symlinks. If either target is a directory or special file, or any operation fails, stop and report the error rather than recursively deleting anything. This replacement is limited to these two project-root files and applies to new projects and existing v3.1 projects. Complete it when the selected branch permits, including after an accepted v3.1 schema with later project-state validation failures. Then run `node <setup-skill-root>/scripts/check.mjs --project-root <project-root> --diagnose` once. This read-only call is the final installation and project-state verification: it checks the payload once, verifies both repaired entry files, and includes ordinary status, the execution-recovery audit, and the cache's current-format check. Require `Payload failures: 0` and `Entry files: pass`; report entry-file or project-state failures as setup blockers without repeating doctor. Do not reproduce a recorded next action from a cache marked stale.
4. Display four labeled sections: **Installation payload** for the initial doctor and final diagnostic-check payload summaries and installed shared reference location; **Project entry files** for the final `Entry files` result, `AGENTS.md`, the relative `CLAUDE.md -> AGENTS.md` link, and validation of registered paths; **Manuscript scope** for the manifest path, registered paths, current scope, current manuscript hashes, and pending action; and **Execution evidence** for approval verification counts, unverified approvals, and shared stale or blocked evidence. Distinguish mechanical execution evidence from operation-specific evidence rather than treating a successful status command as a completed operation. Describe a historical current-draft revision convergence statement as recorded, not verified, unless the selected branch's procedure for that state has been applied. Show the exact host commands for `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, and `revise-request`; for `revise-request`, apply the selected branch's current-draft revision convergence routing rule. Ask the author to confirm host command visibility by checking all five commands in the current host's command palette or autocomplete (in Codex, the `$` autocomplete), or all five exact registered names in its skill picker on a host without skill commands. Explain that the skill the author explicitly starts will confirm the entry operation with the author. Wait for that confirmation and the author's strategy choice.

## Boundaries

Create no manuscript prose and fill in no Story Bible creative content. Except for the two project-root agent entry files described above, preserve existing file contents and historical artifacts. All five strategies use the same manifest, tracker, reports, sessions, backups, handoffs, registered creation path, and shared references installed with this setup skill. Create no strategy-specific state directory. Setup does not alter Git configuration or `.gitignore`.

The six independent skills do not require setup for standalone use. Their standalone contracts live in their own skill directories; the installed shared reference payload does not replace those skill-local files.

Use `$write-fiction`, `$revise-fiction`, `$revise-draft`, `$revise-increment`, and `$revise-request` when displaying the next commands in Codex. Do not add a qualifier to these unqualified registered skill names.

Report setup as ready only when the manifest validates or its concrete errors are reported, all selected paths are registered, the required installed shared references and CLIs are present, and the author has confirmed host command visibility for all five strategies. Do not infer host command visibility from model-facing registry metadata or displayed command strings. Without that confirmation, report host command visibility as unverified and do not report setup as ready. Do not start `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, `revise-request`, or another writing skill from setup.
