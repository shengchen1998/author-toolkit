# Setup Author Toolkit

Register one book project and prepare its shared persistent files. Accept only the project root, an optional manuscript path, and optional language or project metadata. There is no entry-stage or workflow argument. Perform the same setup for every later creation or revision strategy. Use the bundled [controlled workflow terminology](assets/references/terminology.md) for shared terms and exact contract values.

## Setup

1. Inspect the project root with shallow listings and targeted existence or type checks. Look for `.author-toolkit/project.json`, manuscript text files, a Story Bible, an audit tracker, and candidate report, session, backup, handoff, and creation locations. For an existing v3.1 manifest, read `PROJECT_STATE.md` first when present for navigation only, then use `initialize.mjs --project-root <project-root> --json` for the bounded projection and resolved operational paths; leave existence checks to validation. Without a manifest, limit discovery to the candidate component directories and manuscript paths needed for registration; use presence checks or counts that do not emit session or backup filenames. Use `doctor` for installation integrity and the bounded `preflight` or `status` text output for state summaries; do not print `payload-manifest.json`, the complete manifest, or the full backup index. If several plausible roots or manuscript paths exist, present the choices and let the author select one.
2. Register existing paths as they are. Use these defaults only for missing components:
   - `manuscript/`
   - `story-bible.md`
   - `audit-tracker.md`
   - `reports/`
   - `sessions/`
   - `.author-toolkit/backups/`
   - `.author-toolkit/handoffs/`
   - `.author-toolkit/creation/`
3. Keep every shared runtime contract in this installed skill's `assets/references/` payload and resolve it directly from that location. `assets/payload-manifest.json` is the authoritative inventory and SHA-256 manifest for this skill's regular payload files, including every CLI's internal modules and licenses. Run `node <setup-skill-root>/scripts/doctor.mjs --project-root <project-root>` and report its summary. If an installed-payload check fails, report an incomplete toolkit installation and stop. Project-entry mismatches proceed to step 5. Do not maintain a manual file list. Do not copy shared contracts into the writing project. For one combined payload, validation, and ordinary-status check after initialization and entry-file repair, use `preflight.mjs` as described in `author-project`'s read operations; it performs the payload check once and verifies the repaired project entry files alongside project state, without replacing the final verification below. It also checks the cache's current format read-only; do not reproduce a recorded next action from a cache marked stale. For an existing v3.1 manifest, follow this sequence: doctor, initialize, entry-file repair, preflight, then the final doctor in step 5. If preflight validation fails, rerun that command once with `--diagnose` for the bounded recorded-unverified projection, scope paths and hashes, current-hash verification when the scope check passes, and backup-index differences instead of repeating the other inspection commands or printing the complete manifest. Run standalone `validate.mjs` only when a validation failure requires its complete diagnostics; do not repeat it after a successful preflight.
4. For an existing manifest, run `node <setup-skill-root>/scripts/initialize.mjs --project-root <project-root> --json` directly. This is the only existing-project initialization implementation; do not read `author-project`'s initialization references. Once initialization's manifest-schema check passes, perform step 5's entry-file replacement even if later project-state validation fails, then follow it with one `preflight.mjs` call using `--project-root`; report that validation failure as a setup blocker after the repair. Its returned `recorded_unverified` projection and backup-index diagnosis supply the required registered paths and record differences without ad hoc manifest parsing or a separate `read` or `check-index` call. An unsupported or schema-invalid manifest still stops before entry-file replacement. For a new project, read `../author-project/SKILL.md` and `../author-project/references/operations.md`, then follow their new-manifest procedure directly with the selected root and paths, project metadata, and BCP 47 language. Stop for a missing installed file or initialization failure. Preflight's default ordinary status uses the current scope ID when available and leaves unverified approvals nonblocking. Its text summary groups unverified approvals by operation and shows each group's first and last approval IDs; these endpoints do not imply a contiguous ID range. Setup uses ordinary status to inspect state without treating a pending-action operation as a current-draft revision convergence claim. Before relying on a recorded current-draft revision convergence statement to recommend or enter `revise-request`, or to establish a previous scope for `revise-increment`, run preflight again with that explicit `--scope-id` and `--require-execution`; apply the other conditions in [Current-draft revision convergence](../revise-fiction/references/state-and-findings.md#current-draft-revision-convergence). If the strict command exits nonzero, do not present the scope as having reached current-draft revision convergence or recommend a dependent entry. Report the unverified approvals and show `revise-draft` for reconciliation. This execution check does not block ordinary setup, a current-scope review, or unrelated read-only work.
5. On every setup, run `node <setup-skill-root>/scripts/install-entry-files.mjs --project-root <project-root> --json`. This replaces `<project-root>/AGENTS.md` with a regular file containing `assets/AGENTS.md`, and replaces any existing `CLAUDE.md` file or symlink with a relative symlink named `CLAUDE.md` pointing to `AGENTS.md`, so language, explicit-entry routing, and manuscript-safety invariants track the installed toolkit. Detailed strategy routing lives in `ask-author`; operational procedures remain in the active skills and their references. The CLI checks both targets before writing, leaves correct entries unchanged, and atomically replaces other regular files or symlinks. If either target is a directory or special file, or any operation fails, stop and report the error rather than recursively deleting anything. Rerun the same doctor command to verify the installed payload and both entry files. This replacement is limited to these two project-root files and applies to new projects and existing v3.1 projects.
6. For a new project, create missing directories and write only missing skeleton files. Use `../author-project/assets/story-bible-template.md` and the neutral `../author-project/assets/audit-tracker-template.md`. Write supplied project metadata only where the templates request it and leave creative fields empty. Fill the new tracker's project root and manifest timestamp. Leave current scope and pending action unset for the selected skill to establish with the author.
7. For an existing v3.1 manifest, `initialize.mjs` preserves its paths, current scope, pending action, historical evidence, approvals, staged drafts, and backup records while creating only a missing backup index. For a reported backup-index inconsistency after a successful manifest-schema check, complete step 5's entry-file repair before reporting the project-state blocker. Report the record locations and identity differences already returned by `initialize.mjs` or step 3's diagnosis without repeating backup index inspection, repairing history, or inferring a migration; run `node <setup-skill-root>/scripts/writes.mjs check-index --manifest <project-root>/.author-toolkit/project.json --explain` only when the reported inconsistency was not already diagnosed. Make no entry-stage or strategy changes. For any other schema version, report that it is unsupported and stop without changing it. Finish a new project with a separate `validate` call.
8. Display four labeled sections: **Installation payload** for the doctor summary and installed shared reference location; **Project entry files** for `AGENTS.md`, the relative `CLAUDE.md -> AGENTS.md` link, and validation of registered paths; **Manuscript scope** for the manifest path, registered paths, current scope, current manuscript hashes, and pending action; and **Execution evidence** for approval verification counts, unverified approvals, and shared stale or blocked evidence. Distinguish mechanical execution evidence from operation-specific evidence rather than treating a successful status command as a completed operation. Describe a historical current-draft revision convergence statement as recorded, not verified, unless the procedure for that state has been applied. Show the exact host commands for `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, and `revise-request`; for `revise-request`, apply the routing rule in step 4 that requires current-draft revision convergence. Ask the author to confirm host command visibility by checking all five commands in the current host's command palette or autocomplete (in Codex, the `$` autocomplete), or all five exact registered names in its skill picker on a host without skill commands. Explain that the skill the author explicitly starts will confirm the entry operation with the author. Wait for that confirmation and the author's strategy choice.

## Boundaries

Create no manuscript prose and fill in no Story Bible creative content. Except for the two project-root agent entry files described above, preserve existing file contents and historical artifacts. All five strategies use the same manifest, tracker, reports, sessions, backups, handoffs, registered creation path, and shared references installed with this setup skill. Create no strategy-specific state directory. Setup does not alter Git configuration or `.gitignore`.

The six independent skills do not require setup for standalone use. Their standalone contracts live in their own skill directories; the installed shared reference payload does not replace those skill-local files.

Use `$write-fiction`, `$revise-fiction`, `$revise-draft`, `$revise-increment`, and `$revise-request` when displaying the next commands in Codex. Do not add a qualifier to these unqualified registered skill names.

Report setup as ready only when the manifest validates or its concrete errors are reported, all selected paths are registered, the required installed shared references and CLIs are present, and the author has confirmed host command visibility for all five strategies. Do not infer host command visibility from model-facing registry metadata or displayed command strings. Without that confirmation, report host command visibility as unverified and do not report setup as ready. Do not start `write-fiction`, `revise-fiction`, `revise-draft`, `revise-increment`, `revise-request`, or another writing skill from setup.
